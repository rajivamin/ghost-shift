# Ghost Shift: I QA'd the Evaluator Too

**Author-led QA reflection | October 29, 2026 | Original prototype and scorer left unchanged**

I originally built Ghost Shift to investigate what happens when one AI agent disappears and a replacement agent must finish its work from a limited handoff. I used a local Gemma 3 1B model, three fictional workplace scenarios, and a small reference scorer. I also made a short horror film about the experiment.

The first surprise was that the model sometimes reached the expected decision without supporting it correctly. In the Midnight Policy Flip case, it denied a refund for a request made 20 days after purchase, but justified that answer by saying the request was outside a **30-day** policy. Twenty days is within thirty. Its *answer* matched the expected one, while its *reason* contradicted the evidence.

That prompted another question: **If the AI under test can give a convincing but flawed answer, could my scorer make a similarly misleading judgment?**

## Observations from the first four live runs

| Scenario | Expected decision matched? | Full reference checks passed? |
|---|---|---|
| Haunted Inbox, run 1 | Yes: deny | No: required fresh citation absent |
| Haunted Inbox, run 2 | Yes: deny | No: required fresh citation absent |
| Midnight Policy Flip | Yes: deny | No: fresh citation absent; explanation contradicted the old policy |
| Exception Requiring Human Review | No: denied instead of escalating | No: required fresh citation absent |

These observations come from the local run screens and copied model outputs. They are exploratory results, not an independent replication or a model-reliability benchmark. The original run JSON files should be preserved to support later verification.

## Turning the test on the scorer

I examined the original scoring function and submitted four **synthetic scorer probes**, not additional AI-model runs. The evaluator marks a response as passing when (a) its final decision equals the expected action and (b) its `citations` array contains the required source ID.

| Deliberately constructed scorer input | Scorer response |
|---|---|
| Correct decision and source ID, but logically contradictory explanation | **Passed** (false positive) |
| Correct decision and source ID, but explicitly admits guessing | **Passed** (false positive) |
| Correct decision and source ID, but falsely describes what the cited policy says | **Passed** (false positive) |
| Correct decision, but wrong required source ID | **Failed** (correct rejection) |

Separately, all seven original automated tests pass. This does not invalidate those tests; it demonstrates that they covered a narrower set of claims than an organizational reviewer would require.

## What I learned

A correct decision and a cited document ID are **not sufficient evidence** that a decision is grounded, logically coherent, or authorized. The scorer's limited checks were useful for an early prototype, but they could misclassify defective answers as successes.

**I have intentionally left the prototype and original scoring logic unchanged for this submission.** I want reviewers to see what was built, how it behaved, where my assumptions were insufficient, and what independent validation would need to address.

A future, separately reviewed validation process should evaluate source authenticity, whether an explanation actually follows from its evidence, human-approval boundaries, unseen scenarios, reproducibility, and complete execution logs. That would be subsequent work, not a claim about what this version already proves.

**The lesson:** The agent can make an error. The evaluator can, too. Testing the tester is part of responsible experimentation.

---

**Reproduction note:** These QA probes were applied to the unchanged local `ghostshift.engine._grade` scoring function using the `policy-flip` scenario. The four scorer inputs were controlled examples, not generated by the model. No real refunds or other business actions were performed.
